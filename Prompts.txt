Position: Senior AWS Serverless Architect & Cloud Developer
Task: Construct a production-ready, highly secure, and optimized serverless backend for a hybrid B2B/B2C jewelry retail platform using Node.js (TypeScript) and AWS SDK v3.

The architecture must implement the 5 baseline microservices detailed below into standalone, deployable AWS Lambda functions mapped via Amazon API Gateway, backed by a single Amazon DynamoDB table using Single-Table Design patterns.

---

### GLOBAL SYSTEM ARCHITECTURE & IMPLEMENTATION RULES

1. Framework & Runtimes:
   - Language: TypeScript (Node.js 20.x runtime).
   - Bundling: Clean ES Modules targeting AWS Lambda environments.
   - Dependencies: Use native AWS SDK v3 (`@aws-sdk/client-dynamodb`, `@aws-sdk/lib-dynamodb`, etc.). Keep external dependencies minimal.

2. Database Architecture (DynamoDB Single-Table Design):
   - Table Name Pattern: Controlled via environment variable `MAIN_TABLE_NAME`.
   - Core Keys: Partition Key (`PK` - string), Sort Key (`SK` - string).
   - Global Secondary Indexes: Provide one GSI (`GSI1_PK`, `GSI1_SK`) for polymorphic querying.
   - Entity Modeling Mapping:
     * Product Retail: PK: `PRODUCT#<id>`, SK: `METADATA`
     * Product B2B Tier: PK: `PRODUCT#<id>`, SK: `TIER#<org_rating>`
     * Inventory Entry: PK: `INVENTORY#<product_id>`, SK: `STOCK`
     * Cart State: PK: `CART#<user_id_or_business_id>`, SK: `ITEM#<product_id>`
     * Order Entry: PK: `ORDER#<order_id>`, SK: `METADATA`
     * Order Organization Index: PK: `BUSINESS#<business_id>`, SK: `ORDER#<order_id>`

3. Security, Multi-Tenancy & RBAC:
   - Extract user identity contexts exclusively from the API Gateway `event.requestContext.authorizer.jwt.claims`.
   - Distinguish user tiers by custom attributes: `cognito:groups` (contains 'Customer' or 'Organization'), `custom:business_id`, `custom:tax_exempt`, and `custom:credit_limit`.
   - Strict multi-tenant isolation: A user in the 'Organization' group can only fetch or modify states belonging to their specific `custom:business_id`.

4. Fault-Tolerance & Production Rigor:
   - Idempotency Engine: Every mutation request must parse the `X-Idempotency-Key` header. Check against a 5-minute DynamoDB lock record (`PK: IDEMPOTENCY#<key>`, `SK: LOCK`) before processing. If it exists, return the cached payload.
   - Concurrency Safety: All inventory allocations or deductions must use DynamoDB `ConditionExpression` statements to prevent race conditions or double-selling of unique pieces.

---

### SERVICE CODE CONSTRUCTION SPECS

Implement the following routes as distinct Lambda handler functions containing robust input validation (using clean schema guard clauses), comprehensive error handling, and precise HTTP response codes:

#### 1. PRODUCT SERVICE (`/products`)
- `GET /products`: Check JWT claims. If 'Organization', scan/query DynamoDB to include wholesale/exclusive B2B SKUs. If B2C/Public, return only standard items where `is_b2b_only == false`.
- `GET /products/{id}`: Fetch product metadata. If the requesting user is an authenticated 'Organization', dynamically merge the volume-based pricing tier array (`b2b_tiers`) into the returned schema.
- `POST /products`: Guarded to Admin only. Create product entities and write structural pricing records (MSRP + B2B Tier breakdowns).

#### 2. INVENTORY SERVICE (`/inventory`)
- `GET /inventory/{product_id}`: Read real-time metrics showing `available_quantity` and `b2b_allocation_remaining`.
- `PATCH /inventory/reserve`: Atomically reserve items. For unique jewelry (`track_type == "UNIQUE"`), execute a conditional update verifying `reservation_status == "AVAILABLE"`. For bulk components, evaluate `available_quantity >= requested_quantity`. Apply a DynamoDB TTL attribute set to current time + 15 minutes.

#### 3. CART SERVICE (`/cart`)
- `GET /cart`: Resolve the user identity/business ID. Fetch all matching cart items. If the caller is an organization, iterate over items and apply the volume price breaks earned based on the requested item quantity. Return dynamic sub-totals.
- `POST /cart/items`: Add/update items. Block standard 'Customer' group users if they attempt to inject an `is_b2b_only` product ID.
- `POST /cart/bulk-import`: Dedicated route for 'Organization' accounts. Accept an array of SKU/Quantity pairings and batch-write items straight to the DynamoDB cart schema.

#### 4. ORDER SERVICE (`/orders`)
- `POST /orders`: Checkout execution engine. 
  * Validate cart states and invoke internal transactional inventory isolation checks.
  * If B2C: Map order status to `PENDING_PAYMENT` and return an asset token payload.
  * If B2B: Check `total_amount` against the organization's `custom:credit_limit` fetched from the user token context. If it exceeds it, or if verification fails, route status to `PENDING_MANAGEMENT_APPROVAL`.
- `GET /orders` & `GET /orders/{id}`: B2C can only access their specific user ID records. B2B queries search across the entire corporate `business_id` partition key context so company-wide history is accessible.

#### 5. PAYMENT SERVICE (`/payments`)
- `POST /payments/intent`: For B2C clients. Calculate the order total balance, verify payload consistency, and mock a secure Stripe `payment_intent` object returning a client secret.
- `POST /payments/po-verify`: For B2B clients. Verify provided purchase order metrics, evaluate corporate balance margins in DynamoDB, atomically subtract the order balance from the organization's current available credit limit, and update order tracking states.
- `POST /payments/webhook`: Public endpoint verifying signature inputs. Processes payment confirmation callbacks, and updates targeted Order elements to `PAID` via atomic document adjustments.

---

### OUTPUT EXPECTATIONS
Generate clean, well-structured TypeScript modules for each handler. Include concrete TypeScript types/interfaces for all request contexts, API contracts, and internal DynamoDB data schemas. Do not use pseudo-code or omit handling blocks. Implement clear try/catch mechanisms with structured JSON logging on failures.
